Pineapple build plan

How three people build Pineapple in five stages. Inside a stage nobody waits for anyone else. At the end of each stage we merge, run one checklist, and move on.

Version 1.0 · 19 Nov 2026 React + TypeScript Python · FastAPI · LangGraph Gemma 4 12B on Ollama, fully local First course: DBMS
Highlight:

1 How to use this plan

The work is split into five stages. Each stage has three parts, one per person. The parts in a stage are independent: they share only the contracts in section 4, which are written down before anyone starts, and each part uses fakes or mocks for anything another part is building at the same time. When all three parts of a stage are merged, the stage's gate checklist must pass before anyone starts the next stage.

One owner per fileEvery part lists the files it owns. You only edit those. This is what keeps merges clean.
Contracts firstAPI shapes, database tables and internal interfaces are fixed in section 4. Changing them needs all three people (see section 5).
Fakes, not waitingThe backend tests run against a fake model. The frontend runs against mock data. Nobody needs another part to be finished to test their own.
Gate, then goA stage is done when its checklist passes on the model machine. Then we tag it (stage-N-done) and start the next stage.

The three lanes

Each person keeps one lane across stages, so they build up context. In Stage 2 everyone builds whole exercise types end to end (backend and frontend), because those are the most independent units of work. Swap lanes freely if your skills fit better elsewhere.

2 What we are building

Pineapple turns a professor's course notes and syllabus into a 10 to 15 minute practice session for each student, every day. TA and professor comments point out each student's weak spots, and the plan adds a few exercises on them. The AI gives feedback, never grades. The professor sees who is stuck and for how long. Everything runs on one machine with open-weight models.

Product rules the code must enforce

These come from the README. Tests should check each one.

  1. The syllabus drives the plan. Each session covers the current week's topics, plus review of earlier topics that are not solid yet.
  2. Comments only tweak the plan. At most 2 exercises per session target weak points, and weak points never get more minutes than syllabus topics. Sessions never wait for comments.
  3. Sessions last 10 to 15 minutes (target 12), with one exercise of each graded type where the topic supports it, and Ask it last.
  4. Feedback, never a grade. Nothing is written to the LMS. The words "grade" and "score" never appear in the student UI.
  5. Ask it answers only from the course notes. If the notes do not cover a question, it replies with this exact text: "This isn't covered in your course notes. Ask in class or office hours."
  6. Everything is local. The only network traffic is to the Ollama server. No cloud APIs, analytics or CDN fonts in the app.
  7. Raw media stays private. Photos and recordings are visible only to the student who made them, and they are deleted after 30 days. Professors see topic statuses, streaks, sessions, comments and weak points.
  8. "Stuck", never "at risk". The teacher view describes topics and time only.

3 Architecture

3.1 System

One machine runs everything: the Python API, the job runner, SQLite, the media files and Ollama. Browsers on laptops and phones talk to the API over the local network. Anything that calls the model runs as a background job, because a local 12B model takes 5 to 30 seconds per call. The browser polls for the result.

  • Routers validate input, check who is calling, call a service and map the result to a schema. No business logic lives in routers.
  • Services and graphs hold the logic. LangGraph is used where there is a real multi-step AI flow: ingestion, Ask it, comment processing, session generation and exercise evaluation.
  • The model gateway is the only code that talks to Ollama. Everything else uses its interface, so tests and the demo fallback can swap in a fake model.
  • The job runner is a small queue inside the API process, backed by a jobs table. It has no Redis and no Celery. One worker runs by default, because one local GPU can only serve one call at a time.

3.4 Runtime flows

A. Professor adds materials (Stage 1)

  1. POST /courses/{id}/documents saves the file, creates a documents row with status processing and enqueues ingest_document. It returns 202.
  2. The ingest graph routes by kind. Notes: parse, chunk, embed, save, link to topics. Syllabus: extract topics, which wait for review. Video: transcode, transcribe, cut into segments of 60 seconds or less, then summarize each segment from keyframes and transcript. Sample database: install it for the SQL sandbox.
  3. The professor reviews the topics and confirms them with PUT /topics, which relinks the chunks to topics.

B. A comment comes in (Stage 3)

  1. POST /courses/{id}/comments creates the comment and enqueues process_comment.
  2. The comment graph finds related notes, asks the model which topics the comment shows as weak (only from the course's own topic list), saves 0 to 3 weak points and lowers that topic's mastery (it caps it at 0.5).
  3. If today's session has not started yet, it is regenerated. Otherwise the change shows up tomorrow.

C. Daily session (Stage 3)

  1. The student's home screen calls POST /sessions/today, which returns the existing session or starts a generate_session job. Before the demo, make pregen runs this for every student.
  2. The session graph runs the planner, a pure function that picks types, topics and minutes. It then fans out one generation per slot with Send, checks each result, falls back to the hand-written bank if a slot fails, and saves the session as ready.

D. Attempt and feedback (Stage 2, mastery added in Stage 3)

E. Ask it (Stage 1)

Hybrid search finds the top 6 chunks. If even the best chunk is not similar enough, the app refuses without calling the model. Otherwise the model answers using only those chunks and lists the chunk ids it used. Ids that were not in the 6 are dropped. An answer with no valid citation becomes a refusal.

3.5 Model plan and fallbacks

Check this first. Gemma 4 12B is described as taking text, images, audio (up to about 30 seconds) and video (up to about 60 seconds). But Ollama's gemma4:12b listing reportedly shows only text and image input, and it is unclear whether Ollama passes audio to it yet. Part 0B tests every input type on the real setup on day one and records the decisions in docs/model-capabilities.md. The code is built so that each fallback is a config switch.

  • Hardware. The quantized 12B model needs about 8 GB of memory. Use one "model machine" with 16 GB or more (Apple Silicon works well). During development, teammates can point OLLAMA_HOST at that machine on the local network, using demo data only. The demo itself runs on one machine.
  • Context window. Ollama's default context window is small, and longer prompts are cut silently. Always pass options.num_ctx (MODEL_NUM_CTX=16384).
  • Keep it loaded. Set keep_alive to 30 minutes and warm the model up when the API starts, so the first call is not slow.
  • Latency budget. Feedback should usually arrive within 20 seconds. Sessions are generated ahead of time (make pregen) or while the student is on the home screen (1 to 2 minutes).

4.6 Core rules

These are exact so that the planner, progress and teacher view agree with each other. They are pure functions, and each one has a table-driven unit test.

Exercise minutes and order

fix_it 3, trace_it 3, say_it 2, watch_it 3, ask_it 1. Graded types always appear in this order: Fix it, Trace it, Say it, Watch it. Ask it is always last.

When a topic supports a type

  • fix_it: the course has a sample database and "fix_it" is in the topic's exercise_types.
  • trace_it: "trace_it" is in exercise_types.
  • say_it and ask_it: always.
  • watch_it: the topic has at least one clip with question_worthy = true.

Planner: plan_session(inp)

MIN = {fix_it: 3, trace_it: 3, say_it: 2, watch_it: 3, ask_it: 1}
TYPE_ORDER = [fix_it, trace_it, say_it, watch_it]
WEAK_PREF  = [say_it, trace_it, fix_it, watch_it]     # explaining and tracing show misconceptions best

1. due      = topics with week <= current_week   (if none: the topics of the lowest week)
   current  = due topics with week == current_week (if none: due topics of the latest week)
   review   = due topics with week < current_week and status != solid,
              sorted by week desc, then mastery asc
   pool     = current sorted by (missing, partial, solid), then mastery asc; then review

2. Weak-point slots (at most 2 in total):
   weak = open_weaknesses, one per topic, in the given order
   if len(weak) == 1: give that weakness up to 2 slots, using the first 2 supported types in WEAK_PREF
   else:              give each of the first 2 weaknesses 1 slot (first supported type in WEAK_PREF not used yet)
   reason = "weakness", weakness_id set

3. Syllabus slots: for each type in TYPE_ORDER not used yet:
   pick the first topic in pool that supports it, preferring topics not used yet in this session
   reason = "syllabus" if topic.week == current_week else "review"

4. Balance: while (weakness minutes) > (syllabus + review minutes), drop the last weakness slot.

5. Length: total = graded minutes + 1 (ask_it).
   while total < 10: add a say_it, then a fix_it, on the next pool topic that supports it
                     (stop if nothing fits)
   while total > 15: drop the last review slot, otherwise the last weakness slot

6. Order the graded slots by TYPE_ORDER (stable sort), then add ask_it on pool[0]
   with reason "syllabus". Number the positions from 0.
   The result is deterministic: the same input gives the same output.

Demo check: in week 5, Maya has an open weak point on outer joins (a week 4 topic). The planner returns Fix it (GROUP BY, this week), Trace it (outer joins, weak point), Say it (outer joins, weak point), Watch it (GROUP BY, this week) and Ask it. That is 3+3+2+3+1 = 12 minutes. Weak points get 5 minutes and the syllabus gets 6, so the balance rule holds.

Mastery and status

score   = correct 1.0 | partial 0.5 | incorrect 0.0
          (Say it uses its rating: solid 1.0 | partial 0.5 | missing 0.0)
          retakes and failed attempts do not change anything
mastery = mastery + 0.4 × (score − mastery)       # starts at 0.0
attempts += 1
status  = solid    if mastery >= 0.75 and attempts >= 2
          partial  if mastery >= 0.35
          missing  otherwise

New weak point from a comment:  mastery = min(mastery, 0.5), then recompute status
Becomes solid:                  solid_since = now, unsolid_since = null
Stops being solid:              unsolid_since = now, solid_since = null
Weak point resolved:            when its topic becomes solid after at least one attempt
                                on an exercise with that weakness_id

XP, streak, leaves

  • XP per attempt: correct 10, partial 6, incorrect 3 (effort counts). Say it uses solid 10, partial 6, missing 3. Retakes and Ask it give 0. Completing a session adds 10.
  • Streak: the number of consecutive days, ending today, with a completed session. If today has no completed session yet, count back from yesterday.
  • Leaves: the number of solid topics. The pineapple draws at most 12.

Who is stuck, who is inactive

due_date(topic) = course.start_date + 7 × (topic.week − 1) days
since           = progress.unsolid_since or due_date(topic)
stuck  if  topic.week <= current_week
       and status != solid

5 Engineering rules

Branches and PRsName branches s<stage>/<p1|p2|p3>-<slug>, for example s2/p3-trace-it. Keep PRs under about 600 changed lines. Squash-merge into main after one approval from a teammate and green CI.
CommitsUse Conventional Commits: feat:, fix:, test:, chore:, docs:. One logical change per commit.
OwnershipEdit only the files your part owns. If you need a change in someone else's file, open an issue and assign it to them, or note it for the gate. Shared files (main.py, the route table, the mock index) are set up in the kickoff so that nobody needs to edit them later.
Contract changesAdding an optional field: open a PR labeled contract that touches only schemas/ and the regenerated contracts/. One approval is enough. Renaming, removing or changing a type: all three must approve, and everyone rebases the same day. Never break a contract in the middle of a stage.
Backend codeRouters stay thin. Services take a database Session and plain values, never a Request. Graph state holds ids and plain data, never ORM objects. Database access is synchronous and short; model calls are async.
Model callsOnly through ModelGateway.generate(task=..., schema=...), with a prompt file named after the task. No prompt text in Python. Each prompt file has a version; bump it when you change the prompt.
TestsCI runs with MODEL_BACKEND=fake. Tests that need the real model are marked @pytest.mark.model and run by hand on the model machine. Every bug fix comes with a test.
Frontend codeStrict TypeScript with no any. Server calls only go through hooks in features/*/api.ts that use the typed client. Every screen has loading, empty and error states. Components stay under about 200 lines.
PrivacyThe app makes no network calls except to OLLAMA_HOST: no analytics, no CDN scripts or fonts. Do not log photos or audio. Student text answers stay in local logs only.

Definition of done (every part)

  • All steps are done, and the "Done when" checks pass and are pasted into the PR description.
  • make lint and make test pass. New code has tests.
  • No NotImplementedError is left in code this part owns, except stubs that a later stage owns.
  • UI PRs include a screenshot at phone width (390 px) and desktop width (1280 px).
  • Docstrings say why the code does something when it is not obvious, for example thresholds and fallbacks.

Gate protocol (end of every stage)

  1. Each owner opens their final PR with green CI.
  2. The gate captain (rotating: Stage 0 P1, Stage 1 P2, Stage 2 P3, Stage 3 P1, Stage 4 P2) merges in the order P1, P2, P3. After each merge they run make contracts (must produce no diff) and make test.
  3. The captain runs grep -rn "NotImplementedError" backend/app and checks that only later stages' stubs are left.
  4. The captain runs the gate checklist on the model machine with MODEL_BACKEND=ollama. All three people stay available for fixes.
  5. Integration fixes go on a s<N>/gate branch, made together with the owner of the code.
  6. Tag stage-<N>-done and post three lines in the team chat: what works, what was deferred, known issues. Then the next stage starts.
